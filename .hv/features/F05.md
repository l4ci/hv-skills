# F05 — `/hv-freeze` scope lock for parallel orchestrators

## Why

When running multiple `/hv-work` streams in parallel — even with worktree isolation — an orchestrator can drift into files outside its assigned scope. Worktrees prevent two streams from clobbering each other on disk, but inside a single stream nothing stops the orchestrator from refactoring files it was never supposed to touch. The failure mode is loudest during `/hv-refactor` cycles, where the agent has broad license to edit and easily wanders.

Gstack's `/freeze <dir>` solves this in a single-session context: restrict file edits to one directory until `/unfreeze`. Adapt as a per-stream, hook-enforced guard.

## Shape

- `/hv-work` writes its declared file scope to `.hv/locks/<stream>.json` at dispatch (scope derived from the plan or item's stated files, falling back to a prompted glob when unclear).
- A `PreToolUse:Edit` / `PreToolUse:Write` hook reads the active lock for the calling stream and rejects writes outside the declared scope with a clear error.
- `/hv-freeze <stream> <glob>` and `/hv-unfreeze <stream>` for manual control (mid-session tightening or escape hatch).
- Lock auto-released on stream completion or `/hv-pause`.

## Stream identity

Each `/hv-work` orchestrator needs a stable identifier the hook can correlate to a lock file. Options:

- Worktree name (`.claude/worktrees/<name>` → `<name>`)
- Git branch (`dev/<name>` → `<name>`)
- Explicit `--stream <id>` arg on `/hv-work`

Worktree-derived is the cleanest default — already unique, already maps to one stream.

## Hook surface

Hooks run in the harness, not in the agent, so they can hard-block. Requires:

- A hook registered in `settings.json` keyed on `PreToolUse:Edit` and `PreToolUse:Write`.
- The hook receives the target file path and the calling agent's working directory.
- Walks up to find `.hv/locks/<stream>.json`; if found, matches target against scope; rejects on miss.

## Open questions

- What's the scope language? Glob list (`src/foo/**`, `test/**`) or directory list?
- How does the orchestrator declare scope upfront when it doesn't know yet? Maybe lock starts permissive and tightens as files are touched (last-write-wins inside session).
- Should `/hv-refactor` get a different scope contract (broader by design) or use the same mechanism with a wider lock?
- Failure mode: hook misconfigured → all edits blocked. Need a clear "lock active but rejecting everything" diagnostic.

## Cross-references

- Most valuable when paired with multi-stream `/hv-work` and `/hv-refactor`.
- Distinct from worktree isolation — worktrees protect the filesystem between streams; freeze protects intent within a stream.
