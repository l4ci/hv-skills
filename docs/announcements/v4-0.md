# hv-skills 4.0: Claude that doesn't forget

You ran `/clear`. The session is gone. The gotcha you found yesterday — the one that took two hours to track down — is gone with it.

Except in hv-skills it isn't.

That's the whole thing. Everything else is in service of that one promise. v4.0 is the version where we stopped letting it get blurred by anything else.

## Part 1 — The wedge

Working with an AI coding assistant has a structural problem most workflows don't take seriously: every fresh session starts with a brain wiped clean. You spend the first half hour rebuilding context — what the project is, which file has the gotcha, why you chose Postgres over SQLite, what the failing test is actually testing — and then you ask your question. Tomorrow you do it again.

The tools around this problem have mostly been about prompting your way out of it. Better `CLAUDE.md` files. More elaborate system prompts. Read-the-codebase-first agents. None of those answer the actual question, which is: where does *project memory* live?

Not "today's session memory." Project memory. The thing you knew last week, and need to know now, that lives nowhere except in your head and a `git blame`.

hv-skills has had an answer to this since v1. It just wasn't the headline.

`KNOWLEDGE.md` is the durable layer. When you fix something nontrivial, `/hv-learn` writes the gotcha down — topic-grouped, tier-tracked (provisional → confirmed by hit count), and the next time `/hv-work` or `/hv-debug` touches the same area, that bullet is in the worker's brief. The fix gets remembered. The next fix doesn't repeat it.

`DECISIONS.md` is the boundary layer. When you decide *"this codebase uses Postgres, not SQLite, full stop"* — that's a constraint, not a learning. `/hv-decide` writes it with explicit Forbids and Permits, and every plan-time consult after that point respects it. The decision lives in the repo, not in the context window.

`/hv-pause` is the bridge. You're in the middle of investigating a bug, the context window is filling, you `/clear`. The skill writes a handoff note first — the stage you're at, the hypothesis you're testing, the next step you were about to try. On the next `/hv-next`, the handoff is read. The investigation continues. You didn't lose anything.

These three together — KNOWLEDGE, DECISIONS, handoff-across-`/clear` — are the wedge. They are why hv-skills exists. Everything else in the workflow is *the loop around them.*

The loop is short. `/hv-capture` writes work to a backlog (typed, prioritized, ID'd). `/hv-next` picks the next item and routes to `/hv-work`. `/hv-work` plans, dispatches workers in parallel, commits one atomic task at a time. `/hv-review` reads the diff against the plan. `/hv-ship` merges or opens a PR. `/hv-learn` after the cycle. Back to `/hv-next`. The loop is the engine; the wedge is the reason the engine matters.

For three minor versions we treated those two halves — the wedge and the loop — as roughly equal in the documentation. They aren't. The wedge is the thesis. The loop is what makes the thesis useful.

v4.0 is the version where we stop pretending otherwise.

The change isn't in the wedge. KNOWLEDGE, DECISIONS, and handoff-across-`/clear` have been there since v1. The change is in the surface around them. v3 shipped twenty-eight commands because every time we discovered a useful flow we minted a new slash. After a while the README read like a wall of features and the mental model demanded that you remember which command did what. That's adoption friction, and it lives entirely on the loop side. The wedge wasn't getting any worse. The loop was getting harder to see.

v4 fixes the surface. Twenty commands instead of twenty-eight. Every cut routed to a flag on a surviving command. Every fold tested against the same backlog the cuts were captured in. The wedge stays exactly where it was; everything orbiting it gets compressed.

You don't have to take our word for what the wedge feels like. Run `/hv-init` on a project. Write a learning. `/clear`. Run `/hv-next`. The learning is in the next worker's brief. That's the contract. The cuts in v4 are the work of making that contract easier to see.

So when you ask what v4.0 is, the honest answer is: it's the version where we removed eight commands. But naming it that way frames it as loss. It isn't. The eight commands were a tax we collected from every new user — every README scan, every *"wait, what does `/hv-undo` do"* — and the wedge they were taxing wasn't getting any closer in return. We stopped collecting.

## Part 2 — The cut

A workflow has a complexity budget. Every command you add charges the user once at discovery, once at documentation, once at onboarding, and once every time they remember it might exist. That's a recurring tax on the loop, paid in attention.

v3 spent the budget on aliases and conveniences. `/hv-c` was a typing shortcut for `/hv-capture`. `/hv-undo` was a separate skill for a rollback that conceptually belonged in `/hv-ship`. `/hv-issues` was a third entry point alongside `/hv-capture` and `/hv-go`, each with its own register of when to use which. None of them were broken. All of them charged a tax that wasn't earning its keep.

v4 spends the budget once, in the right places.

`/hv-c` is gone — so you don't have to wonder whether `/hv-c` and `/hv-capture` do different things. They didn't. The alias was muscle memory; muscle memory will adapt.

`/hv-assume` is folded into `/hv-work --preview <ID>` — so the read-only *"what would you do here"* path lives next to the read-write *"do it"* path, not in a separate command you might forget exists.

`/hv-rm` is folded into `/hv-capture --remove <ID>` — so removing an item from the backlog is the inverse of capturing one, on the same skill, with the same banner.

`/hv-undo` is folded into `/hv-ship --undo` — so rolling back the last cycle is a flag on the skill that landed it, not a separate skill you have to remember after the fact.

`/hv-issues` is folded into `/hv-capture --from-github` and `/hv-capture --from-gitlab` — so pulling upstream tickets into the backlog is the same shape as pulling anything else into the backlog.

`/hv-context` is folded into `/hv-learn --term <name>` — so domain terms (*"what does 'umbrella' mean in this repo?"*) and durable knowledge (*"never skip pre-commit hooks"*) live in the same file, under the same skill, with the same lifecycle.

`/hv-map` is folded into `/hv-init` (first run) and the cycle skills (`/hv-work`, `/hv-debug`, `/hv-go`) for after-work updates — so the subsystem index gets built when you initialize the project and maintained passively by the cycle, without a dedicated command sitting between you and the work.

`/hv-docs` is folded into `/hv-ship --docs` and an auto-trigger when `docs/` exists — so public docs stay in sync with code at ship time, when the diff is already loaded, not in a separate ceremony you forgot to run.

That's eight cuts. They map to eight smaller mental models that have always existed inside the loop. Removing them doesn't change what you can do. It changes how much you have to hold in your head to do it.

### Migration

There's exactly one command you need:

```
/hv-migrate v4
```

It rewrites `.hv/BACKLOG.md`, `.hv/plans/*`, `.hv/designs/*`, `.hv/handoff/*`, `.hv/qa/*`, and the project `CLAUDE.md` from v3-shape names to v4-shape names. Dry-run is the default — pass `--apply` to write. Idempotent. Every touched file is backed up to `.hv/migrate-backup/<timestamp>/` before any rewrite.

That's it. No deprecation window. No alias stubs. No deprecation warning output bloating every session for six months. The codemod is the safety net; the cuts are clean.

Twenty commands left. You know what they all do.

### What hv-skills will not become

We name these to set expectations, not to apologize for them. Trust comes from knowing what a tool is shaped like, including the shape of its negative space.

**hv-skills will not become a multi-provider workflow.** Single-provider (Claude Code) is the chassis. If you want cross-model debate, [Octo](https://github.com/anthropics/octo) is built for that.

**hv-skills will not become a phase-gated methodology.** The loop is a loop, not a pipeline. If you need formal discuss/plan/execute/verify/audit sign-off, GSD fits that shape.

**hv-skills will not become a project tracker.** The backlog exists to feed the loop, not to be a standalone tracker. Linear and Jira do the tracker job better; hv-skills can pull from either via `/hv-capture --from-github` and friends.

**hv-skills will not federate KNOWLEDGE across projects.** One project, one knowledge layer. Per-project memory is the contract; "company-wide AI knowledge" is a different product with different tradeoffs.

**hv-skills will not become a build system or a test runner.** It calls your build and test commands; it doesn't replace them. `/hv-qa` runs your runners. It doesn't ship its own.

### Upgrading

```
npx skills add l4ci/hv-skills
/hv-migrate v4
```

That's the upgrade path. The first command brings v4 onto your machine. The second rewrites your project's `.hv/` state in place.

If you're new — `/hv-init` once at the project root, then `/hv-next`. The loop runs itself.
