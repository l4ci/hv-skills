# 5.0 `hv` verb contract

This file defines every `hv` verb's arguments, flags, `--json` data and exit codes. The black-box smoke suite (A2, #46) tests against it, and the Go port (A3 to A9) implements it. Verbs come from the command tree in the [helper triage](5.0-helper-triage.md). Global flags, the JSON envelope, stderr format, the exit-code table, write rules and config loading are fixed by the [CLI conventions](5.0-cli-conventions.md) (A3, #47). Nothing here overrides them: failure `data` on exit 1 and 4, exit 4 for mutating verbs only, and `changed` in failure data all come from the conventions.

Status: **reviewed by the maintainer on 2026-10-02, who signed off on the defaults pending the changes now applied** (quote: "Defaults + you verify"). Arguments were redesigned on purpose (maintainer, 2026-10-02: "Redesign arguments now"), so many verbs differ from the helper they replace. During the port, `test/hv-shim` translates each new-shape call into the old helper call. The `old:` line under each verb is the shim's mapping.

## Per-verb rules

These rules fill in what the conventions leave to each verb. Every verb below follows them, and any exception says why.

1. **Positionals are for the thing the verb acts on**: an item ID, a key, a topic, a name. Everything else is a flag. A verb takes at most one kind of positional. A kind is a category, not the target, so `kind` is always the flag `--kind` (`hv id next --kind bugs`, `hv item create --kind bugs`). Setting a state or status is `--to <value>` everywhere (`item state --to`, `milestone status --to`).
2. **Lists.** Several targets of the same kind are variadic positionals (`hv backlog milestones B01 F02`), never one comma-joined argument. A list carried in a flag is comma-separated (`--repos a,b`); no flag is repeatable.
3. **Bodies** come from `--body-file <path|->`, never from positional text or inline flag values. A verb that already takes `--body-file` and needs a second, different file input names it after its content; the only case is `item create --raw-file`, the preformatted bullet. Short single-line values (title, summary, note) are flag values: `--title`, `--summary`, `--note`.
4. **Families share one shape where the verb exists.** milestone, plan, design and spike use `add` (create; refused with exit 4 if the key exists), `list`, `show <key>`, `put <key> --body-file`, `rm <key>`. The key is always the first positional. Not every family has every verb: milestone has no `rm` (it ends as `archived`), spike has neither `put` nor `rm` (`finish` ends it), and `milestone add` mints its key.
5. **Preview before bulk rewrites.** Verbs that rewrite many files, history or several items at once (`migrate v4`, `migrate issues`, `ship undo`, `item rm`) only report what they would do unless `--apply` is given. Every other mutating verb acts directly. No verb uses `--dry-run`, `--force` or `--yes`. A preview that writes nothing adds the warning `preview only; pass --apply` to `warnings`.
6. **Check verbs** answer a question: guards, gates, `has`-style lookups. Exit 0 means the predicate in the verb's name holds (`item ready` is ready, `git guard clean` is clean, `item shipped` found evidence); every other answer is 1. `data` carries the answer (a named boolean or a verdict) on both exits (conventions: failure data). `--json` callers never need the exit code.
7. **Verdict vs check.** A classifier verb (`worker poll`, `update`, `version --drift`, `plan validate-docs`) returns its verdict in `data` and exits 0 whatever the verdict. A check verb exits 0 when the predicate in its name holds and 1 for every other verdict, with the verdict in `data`. The predicate is the one the name asks: `plan uncertain` exits 0 when the item is uncertain, `item shipped` when ship evidence is found, `worker gate` when the gate passes, `worker session check` when inside a managed session, `worker reset --check-only` when the slot holds no work. The check verbs are `config check`, `repo umbrella`, `item ready`, `item shipped`, `plan uncertain`, `knowledge contradiction has`, `worker gate`, `worker session check`, `worker reset --check-only`, `worker account pick`, `git guard clean`, `git guard feature-branch`, `release milestone-check`, `init check` and `doctor`. A mutating verb that declines to act exits 4 (`worker reset` without `--check-only`, `release bump` to a version that is not greater, `ship pr-merge` with an unproven item, `item complete` without proof, any gated verb whose manual gate is not cleared, `ship pr`, `ship merge` or `ship pr-merge` after a recorded FAIL, a debug attempt past the Iron Law), and its failure `data` says what blocked it. `worker gate` is a check verb that still exits 4 on a manual-gate refusal (B1), because it refuses before judging anything. A verb that changed state on the way to exit 1 or 4 (`worker gate` after a merge, `ship pr-merge` recording `changes-requested`) reports `"changed": true` in its failure `data`. A read-only verb never exits 4.
8. **Text output** is one human line per result, or the body of the requested file for `show` verbs. The contract defines only `--json` data. Smoke asserts on `--json` except where it checks that a `show` verb prints the stored body verbatim.
9. **`--repo` is global.** Each verb states whether it is repo-scoped. A verb with no repo scope rejects `--repo` (exit 2), per the conventions. On a repo-scoped verb, a name that is not a registered sub-repo exits 3 (`resolution`) before any check of the verb's own, so an entry's "`--repo` exits 2" means a registered name the verb does not accept.
10. **No test-only flags.** Fixture hooks the old helpers carried as flags (`--fixture`, `--status`) become environment variables named `HV_TEST_*`, which the contract lists per verb and which are not part of the CLI.
11. **Item IDs** are strings in `data`. File mode: `"B07"`. Issue mode: the issue number, `"12"`. Umbrella issue mode: `"<repo>:12"`. Every `data` object that names an item by `id` also has `type` (`"B"`, `"F"` or `"T"`) in both modes, so the type letter is never lost; rows inside the `bugs`, `features` and `tasks` lists of `backlog list` are already grouped by kind and omit it. Lists of bare IDs (`ids`, `items` as `[]string`) use the same `id` spelling and carry no types. Inputs accept every form the old helpers accepted (`B7`, `#7`, `7`, `repo:B7`, `repo#7`). A flag that carries a list of item IDs is always `--items <ID>[,<ID>…]`.
12. **Data shapes.** A list verb wraps its list in an object keyed by a domain noun (`{"items": […]}`, `{"plans": […]}`). A verb whose subject is one item names it `id`. Every mutating verb reports `changed`.
13. **Flag names.** No verb flag reuses a global flag's name (`--json`, `-C`/`--cwd`, `--repo`, `-h`/`--help`), as the conventions require.

## Verb entry format

```
### hv <group> <verb>
hv <group> <verb> <positional> [--flag <value>] [--bool]
repo: scoped | none
data: {"field": type, …}
exit: 1 when …; 3 when …; 4 when …
old: hv-helper <args in old order>    (shim mapping)
shim: how the shim builds `data` and maps old exit codes    (optional)
note: …    (optional)
env: HV_TEST_* hooks    (optional; rule 10)
```

Field types use JSON names (`string`, `number`, `bool`, `object`, `[]string`). `?` after a field name means it may be absent. Exits 0, 2 and 70 are implied and not listed. `exit: implied only` means the verb adds no other code.

## Shared definitions

Entries use these names instead of restating them.

- **scope S.** A repo-scoped verb's scope. `--repo <name>` selects a registered sub-repo. With no `--repo`, S resolves from the working directory: inside a registered sub-repo it is that sub-repo, otherwise the umbrella, as the old `hv-knowledge-scope.sh` did. To reach umbrella scope from inside a sub-repo, pass `-C <umbrella root>`. Outside umbrella mode S is always the project.
- **text-read data.** `{"text": string, "missing"?: []string}`. `text` is the stdout the old helper printed (also what text mode prints). `missing` lists requested names that matched nothing. The shim cannot compute `missing` for helpers that don't report it, and omits it there.
- **`backend` in an `exit:` line.** The verb works on one backlog backend only (`backlog.backend` `file` or `issues`) and was called under the other. A mutating verb exits 4 `refused`; a read-only verb (no `changed` in its `data`) exits 1 `failed`, because the conventions forbid exit 4 for read-only verbs. Either way the failure data is `{"blockedBy": "backend", "changed": false}`, and the hint names the verb to use instead when one exists. Old backend helpers exited 2 for this.
- **`tracker` in an `exit:` line.** Exit 5 `unavailable` when the tracker or forge CLI is missing or failing, exit 6 `retry` when it rate-limits. Old backend helpers exited 3 and 4 for these.
- **Failure data.** Exit 1 carries the verb's answer in `data`, which is the same shape as its success `data` unless the entry says otherwise. Exit 4 carries `{"blockedBy": string, "changed": bool}` unless the entry defines more: `blockedBy` names the invariant in one word or phrase (`exists`, `base branch`, `proof missing`, `backend`), and `changed` is true only if the verb changed state before refusing. Every other failure sends `error` alone (conventions).
- **Invalid `backlog.backend`.** A value other than `file` or `issues` is a corrupt config: every verb that reads the backend exits 70.
- **Lock timeout.** Every verb that writes a state file exits 6 when the lock times out (conventions). Entries don't repeat it.
- **Old backend rc mapping.** Unless an entry says otherwise, the shim maps an old backend helper's rc 1 to 3 when stderr says `not found` and to 2 for bad arguments, rc 2 to 4 (`backend`), rc 3 to 5 and rc 4 to 6 (`tracker`).
- **Umbrella issue mode IDs.** `<repo>:<ID>` and `<repo>#<n>` always resolve. A bare ID that exactly one sub-repo holds resolves to it, as the old helper did (`_pick` in `bin/hvlib_backend.py`). A bare ID that several sub-repos hold (`F42`, `#42`) is exit 2, and the message lists the qualified candidates in the `data.id` spelling (`ghrepo:42, other:42`). The global `--repo` selects a sub-repo scope for the verb and never rewrites an ID. The shim maps the old TrackerError rc 1 with `ambiguous across sub-repos` to 2.
- **Dual spelling.** The backend still writes the old spelling. `bin/hvlib_backend.py` renders the issue bullet head as `**[{letter}{number}] …**` (line 714) and returns `f"{letter}{number}"` from create (lines 857 to 858, where the `{ID}` placeholder in the issue body is also replaced by it), so commits, PR bodies and issue bodies carry `[B7]`. A caller maps `[B7]` to `id` `"7"` by dropping the type letter; the letter is `type`. This PR does not change the backend's write format. The shim does the mapping when it builds `data`.
- **Checkout verbs under `--repo`.** A repo-scoped verb that reads or writes a git checkout or files in it (`release version|bump|host|changelog|pending`, `release notes --from commits`, `git`, `review` and `ship` verbs) runs in the named sub-repo's checkout, not at the umbrella root.
- **Commands that run without `.hv/`.** The conventions name `hv init` as running without a project root. `init check` and `init umbrella` count as part of it: they act on the working directory after `-C`, with no walk-up.
- **`slot`** (A7 verbs, which all act on `.hv/workers.json` at the project root). `{"name": string, "branch": string, "worktree": string, "base": string, "handle"?: string, "state": string, "task"?: string, "pr"?: string, "relays": [{"round": number, "ts": string, "summary": string}], "configDir"?: string, "account"?: string}`. Null registry fields are absent in `data`.


## A3 and A4: version, update, config, repo

`hv version` ports in A3 (#47). `hv update`, `hv config` and `hv repo` were routed to A4 (#48) after the triage; their shapes stay here.

### hv version
hv version [--drift]
repo: none
data: {"version": string}; with `--drift`: {"version": string, "stamped": string, "installed": string, "status": "match"|"drift"|"unknown", "drift": bool}
exit: 3 when `--drift` and no `.hv/` is found. `status` is `unknown` when `stamped` or `installed` is empty.
old: plain `hv version`: hv-resolve-plugin-root --root-only (no positional or flag maps; prints the plugin root). `--drift`: hv-version-check --json (new `--drift` selects the old `--json` form; no other args).
shim: plain form reads `version` from `<root>/.claude-plugin/plugin.json` at the printed root; `--drift` wraps the old JSON (`stamped`, `installed`, `status`) and adds `version` (= `installed`) and `drift` (= `status == "drift"`); an old rc 0 with empty output (no `.hv/`) becomes exit 3.
note: `stamped` is `hvSkills.version` from the merged config; `installed` is the running binary's embedded version (old: plugin.json at the resolved plugin root). In 5.0 they are the same source, so `version` and `installed` are equal.
note: old `hv-version-check` exited 0 silently without `.hv/`, where 5.0 exits 3.

### hv update
hv update
repo: none
data: {"installType": "plugin"|"stow"|"repo"|"override"|"unknown", "installRoot": string, "currentVersion": string, "latestVersion": string, "status": "behind"|"current"|"ahead"|"unknown", "updateCommand": string}
exit: implied only. A missing `gh`, a network failure or an unresolved install gives `latestVersion` or `currentVersion` empty and `status: "unknown"`, as old. Read-only: never runs the update.
old: hv-update-check (no args). Env: `HV_INSTALL_ROOT` stays as the real override (`installType: "override"`, not a test hook); `HV_TEST_LATEST_VERSION` is the shim's name for old `HV_LATEST_VERSION` (rule 10).
shim: old stdout is already this JSON; pass it through unchanged and export `HV_LATEST_VERSION="$HV_TEST_LATEST_VERSION"` when set.
note: strings may be empty rather than absent, as in the old helper.
note: `currentVersion` is the installed plugin's version: `version` from `.claude-plugin/plugin.json` under the resolved install root (`HV_INSTALL_ROOT`, `CLAUDE_PLUGIN_ROOT`, then the old hv-update-check resolution), as old read it, and empty when that file has none. Only when no install root resolves is it the binary's stamped version (orchestrator ruling, A4 acceptance).

### hv config show
hv config show [<key>]
repo: scoped
data: {"entries": [{"key": string, "value": any, "source": "local"|"project"|"default"}]}
exit: 3 when `<key>` is neither a schema key nor present in the merged config; 2 when more than one positional is given. `value` is the raw JSON value (not a JSON string of it). No key: every schema key in schema order. With a key: `entries` holds exactly one element, so both forms share one shape.
old: hv-config-show [<key>] (new `<key>` maps to the old single positional; unchanged).
shim: parse each stdout line with `^(\S+) = (.*)  \(source: (local|project|default)\)$` into `key`, `value` (JSON-parsed), `source`; old rc 1 with `unknown key` on stderr becomes exit 3, rc 1 with `usage:` becomes exit 2.
note: old rejected any key outside the schema table. 5.0 accepts a key that is in the schema or present in the merged config, so a hand-edited key stays readable (`config set` itself is schema-only). The shim cannot do this; it fails with exit 3 as before.

### hv config set
hv config set <key> <value>
repo: scoped
data: {"key": string, "value": any, "previous"?: any, "changed": bool}
exit: 2 when `<key>` is not in the schema that `config check` uses (the shared table in `bin/hvlib_config.py`), is a malformed path (empty segment: `""`, `.a`, `a.`), or an argument is missing; 70 when `.hv/config.json` exists but is not a JSON object, or the write fails.
old: hv-config-set <key> <value> (both map to the old positionals in order). Writes `.hv/config.json` only, never `config.local.json`. `<value>` is parsed as JSON first (`true`, `42`, `"x"`, `[…]`, `{…}`) and falls back to a raw string (`opus`, empty string). `previous` is the stored value before the write and is absent when the key was unset.
shim: old accepts any key, so the shim checks `<key>` against the schema table first and exits 2 without calling the helper when it is absent; old stdout is empty; read `.hv/config.json` before and after the call to fill `value`, `previous` and `changed`; old rc 1 with `malformed key path` on stderr becomes exit 2, rc 1 for missing argv becomes exit 2, any other rc 1 becomes exit 70.
note: the JSON-then-string coercion is kept because `hv-init` and `hv-config` skills depend on it. A string that looks like JSON (`"true"`) still needs shell quoting (`'"true"'`). No `--string` or `--local` flag is added.
note: a key outside the schema is rejected (maintainer decision), where old accepted any key.
note: an empty `<value>` is valid and stores the empty string; the old helper rejected it, so the shim passes `""` as a JSON literal.

### hv config check
hv config check
repo: scoped
data: {"status": "upToDate"|"fresh"|"stale"|"corrupt", "upToDate": bool, "missing": []string}
exit: 1 when `status` is anything but `upToDate` (`fresh`, `stale` or `corrupt`); 3 when no `.hv/` is found. `missing` lists dotted required keys that are absent or null, in schema order, and is non-empty only for `stale`. `fresh` means `config.json` does not exist; `corrupt` means it is invalid JSON or not an object (this is a defined verdict, so it does not use exit 70).
old: hv-config-schema-check (no args).
shim: map stdout `UP_TO_DATE` to `status: upToDate`, `FRESH` to `fresh`, `CORRUPT` to `corrupt`, and `STALE:a,b` to `stale` with `missing` = the split list; exit 0 for `upToDate`, else 1 (old always exited 0).
note: old always exited 0, so skills that branch on the four tokens must read `data.status`.

### hv config fill
hv config fill
repo: scoped
data: {"filled": []string, "changed": bool}
exit: 3 when no `.hv/` is found; 70 when `.hv/config.json` exists but is invalid JSON or not an object (`config check` status `corrupt`), and nothing is written.
old: none (A9 addition, G1; replaces the ~20 default `config set` calls the hv-init skill carried as prose).
note: writes the schema default (`config show`'s `source: default` value) for every required key that `config check` lists in `missing`, so `config check` reports `upToDate` afterwards. `filled` lists those keys in schema order. A missing `config.json` is created holding every required key. Keys already present, keys outside the schema and `config.local.json` are never touched. Nothing missing gives `filled: []`, `changed: false`, and the file is not rewritten.
note: each added key goes in at its schema position among its siblings: before the first existing sibling that comes later in schema order (an object's position is that of its first schema key), so a file that starts in schema order stays in it (G7). Siblings outside the schema keep their place. The file is written as `config set` writes it (two-space indent).
note: `umbrella.enabled` and `hvSkills.version` are required, so `fill` writes their defaults (`false`, `""`) when they are missing. Callers that know better set them with `config set`; `config set` on a present key keeps its position. The init skill runs `hv init`, then `hv config fill`, then `config set` for the answered keys, which keeps the file in schema order.

### hv repo which
hv repo which
repo: none (the answer comes from the working directory)
data: {"name": string, "path": string}
exit: 3 when the working directory is not inside a registered sub-repo, is not in a git repo, there is no umbrella, or a stray `.hv/` inside a registered sub-repo masks the umbrella (`error.message` says which, and the hint names the stray `.hv/`); 5 when `git` is missing. `path` is the absolute realpath of the registered sub-repo root (a Layout B worktree maps to its main repo).
old: hv-resolve-repo (no args; run from the same working directory, `-C` becomes `cd`).
shim: old stdout is the name; fill `path` by running `hv-resolve-repo-path <name>` from the umbrella root printed by hv-resolve-umbrella; old rc 1 maps to 3, including the `masking` case.
note: the triage tree writes name-to-path as `hv repo which --path`. That shape is dropped: `which` now returns both name and path, and the name-to-path lookup is `hv repo resolve <name>`, so hv-resolve-repo-path (merged) needs no flag.

### hv repo resolve
hv repo resolve [<name>…]
repo: none (reads the umbrella registry)
data: {"repos": [{"name": string, "path": string}]}
exit: 3 when any name is not registered, or the project is not an umbrella (empty registry); `error.message` names every unregistered name. No names gives `{"repos": []}` and exit 0, as the old helper did for `""`. Order follows the arguments, duplicates preserved; `path` is the absolute realpath.
old: hv-resolve-repos "<names joined by comma>" (variadic positionals become the one comma-joined old positional; zero names become `""`). Run from the umbrella root.
shim: wrap the old stdout JSON array as `{"repos": [...]}`; old rc 1 becomes exit 3.
note: the triage tree writes `resolve <csv>`; rule 2 makes it variadic. Merged hv-resolve-repo-path (`<name>` to path) is `hv repo resolve <name>` and reads `repos[0].path`.

### hv repo umbrella
hv repo umbrella
repo: none
data: {"umbrella": bool}
exit: 1 when the project is not an umbrella (no `.hv/`, no `.hv/repos.json`, or an empty registry). It never exits 3 for a missing `.hv/`: no root means no.
old: hv-umbrella-on [<dir>] (new `-C <dir>` global flag replaces the old optional positional; no positional remains).
shim: map stdout `yes` to `umbrella: true` and exit 0, `no` to `umbrella: false` and exit 1; pass `-C <dir>` as the old positional.
note: umbrella status is true iff `.hv/repos.json` holds at least one entry, and `umbrella.enabled` is ignored, same as old. The old positional dir is dropped for `-C`; unlike old, discovery walks up to the nearest `.hv/` (conventions).


## A4: backlog, capture, IDs, status

### hv id next
hv id next --kind <bugs|features|tasks|milestones>
repo: scoped
data: {"kind": string, "id": string, "changed": bool}
exit: 2 when `--kind` is missing or not bugs|features|tasks|milestones; backend (file-only: issue mode IDs are issue numbers)
old: hv-next-id <kind>    (`--kind` is the old positional)
shim: `id` is the printed ID, `changed` is always true (the counter is written).
note: `--kind` is a flag, as in `item create` (rule 1). Exception to rule 11: `id` is a fresh counter ID and `kind` already gives the type, so there is no `type` field.

### hv item create
hv item create --kind <bugs|features|tasks> --title <text> [--tag <tag>] [--desc <text>] [--body-file <path|->] [--related <text>] [--milestone <text>] [--repos <csv>] [--subsystem <text>] [--captured <YYYY-MM-DD>] | --kind <kind> --raw-file <path|->
repo: scoped
data: {"id": string, "type": "B"|"F"|"T", "kind": string, "detail"?: string, "changed": bool}
exit: 3 when BACKLOG.md or its section is missing, `--body-file` or `--raw-file` cannot be read, the milestone is absent on the tracker, or the umbrella repo is unknown or ambiguous; backend (`--raw-file` is file-only); tracker

## B2: verdicts

B2 (#55) replaces "parse the last line" routing in `/hv-review`, `/hv-qa`, `/hv-ship` and `/hv-debug` with typed verdicts: the skill records each verdict through a verb, which validates it, and the routing from verdict to next step is a tested function in code. B3 (#56) builds on the store: `ship pr` and `ship merge` refuse after a recorded FAIL, and the debug Iron Law counts failed fixes per item.

- **Verdict store.** `.hv/verdicts.json`, at the project root (the umbrella root in umbrella mode), gitignored per developer like `status.json` (`hv init` adds the line to its managed `.gitignore` block). Shape: `{"branches": {"<key>": [record, …]}, "items": {"<id>": [record, …]}}`. A branch key is the branch name, or `<repo>:<branch>` for a sub-repo branch (git forbids `:` in ref names, so keys never collide). An item key is the ID as given to the verb. Records are appended oldest first, and each list keeps its latest 20. The file follows the conventions' write rules (atomic, locked read-modify-write).
- **record.** `{"kind": string, "verdict": string, "combined"?: string, "branch"?: string, "repo"?: string, "sha": string, "recordedAt": string, "summary"?: string, "findings": [finding], "items"?: [{"id": string, "verdict": string}]}`. `sha` is the short tip of the branch (HEAD for debug) when the verdict was recorded; `recordedAt` is UTC ISO 8601. Item records carry no `branch` or `repo`. `combined` is stored on `review-quality` records only (see `verdict add`).
- **kinds and their verdicts.** `review-spec`, `review-quality` and `second-opinion` take `PASS`, `CONCERNS` or `FAIL`; `qa` adds `INFRA-FAIL`; `debug-fix` takes `PASS` or `FAIL`. Worst-of order is `PASS` < `CONCERNS` < `FAIL` < `INFRA-FAIL`.
- **body.** `--body-file` is optional and holds a JSON object `{"verdict"?: string, "summary"?: string, "findings"?: [finding], "items"?: [{"id": string, "verdict": string}]}`. A `finding` is `{"severity": "blocker"|"major"|"minor"|"info", "title": string, "file"?: string, "line"?: number, "detail"?: string}`. Validation is strict: an unknown key, a wrong type, an empty `title`, a `line` below 1, a `severity` or `items[].verdict` outside its set, or text that is not one JSON object is exit 2, and the message names the field. `--verdict` is always required; a `verdict` in the body must equal it (exit 2 otherwise), so a reviewer's JSON block can be passed through whole.
- **effective review verdict** of a branch. The latest `review-quality` record's `combined`, unless a `review-spec` record is newer, in which case that record's `verdict` (a spec-only review, or a spec FAIL that skipped Stage 2). `verdict route --for ship-review` and B3's ship refusal read it.
- **stale.** A record is stale when its `sha` differs from the branch's current tip. Routing reports it and does not change `next` because of it.

## B1: manual gates

B1 (#54) moves the manual gates out of skill prose and into the verbs. Orchestrator rulings (round 4, phase B, from the maintainer on 2026-10-03): a gated verb exits non-zero without `--confirm` at every autonomy level; skills pass `--confirm` only after an `AskUserQuestion` yes; every confirmed pass is appended to an audit log under `.hv/` with the gate, the verb, the time and the quoted human answer (`--confirm-note`, required with `--confirm`). Issue close and issue label are not gated in code. Gated: tag push, release publish, public filing (`tracker suggest-upstream`), and merges where config requires human approval (all merges, or merges touching listed paths, per #44 "Merging").

- **Registry.** One table in `internal/gate` names every manual gate the skills describe, enforced or not. `hv gate list` prints it. Any other `ship.mergeApproval` value is exit 2 on a merge verb, never a silent `none`.

## B3: verdict refusals, the Iron Law, loop-only flags

B3 (#56) moves three prose rules into the verbs. Orchestrator rulings (round 4, phase B, from the maintainer on 2026-10-03): ship refuses after a recorded review or second-opinion FAIL, except under the advisory codex fallback (#158); the Iron Law is a per-item counter, and a 4th attempt is refused until `hv debug reset <ID>`, a B1 gated verb (`--confirm` plus `--confirm-note`, audited, with a reason); `--auto-loop` outside loop mode is a usage error (exit 2).

- **Ship refusal.** `ship pr` and `ship merge` read the branch's records in the B2 store (key as `verdict add` builds it). The branch is blocked when its effective review verdict is `FAIL`, or its latest `second-opinion` record is `FAIL` and `ship.secondOpinionRunner` is not `codex`. A stale FAIL still blocks: only a newer record of the same kind clears it, so a fix is reviewed again before it ships. `CONCERNS` and QA verdicts never block here; their routing stays with `verdict route`. A branch with no records ships as before. The refusal is exit 4 before anything changes, with failure data `{"blockedBy": "verdict", "kind": string, "verdict": "FAIL", "sha": string, "stale": bool, "changed": false}` (`kind` is `review-spec`, `review-quality` or `second-opinion`; review is checked first). The hint names `hv verdict show`. `ship pr-merge` (the `/hv-review --queue` merge path) applies the same refusal to the PR's head branch, read from the forge's open-PR listing the verb already makes; in umbrella mode the key is `<repo>:<branch>` for the `--repo` sub-repo. When the forge reports no head branch, the verb does not refuse and adds the warning `could not resolve the head branch of PR <n>; verdicts not checked`. `worker gate` is not covered.
- **Iron Law.** The count is per item: the item's `debug-fix` FAIL records in the store since its latest `debug-reset` record, the same number `debug verdict` reports as `failedFixes`. A new branch or a cleared session file does not reset it. At 3 or more, `debug counter init <ID>` and `debug counter record-attempt` (which reads the item from the session's `bug_id`) exit 4 with failure data `{"blockedBy": "iron law", "bugId": string, "failedFixes": number, "changed": false}` and the hint `hv debug reset <ID>`. `debug verdict` is never refused: an outcome is always recorded.
- **Loop-only flag.** `--auto-loop` on `design add` and `plan add` marks the artifact as written by a loop run: the verb adds `auto: true` to the frontmatter, after `status:`. It is exit 2 unless `autonomy.level` (config.local.json over config.json) is `loop`, checked before anything is written. These two verbs are where a loop-mode `/hv-brainstorm` or `/hv-plan` run leaves its mark; the skills' own `--auto-loop` argument is not a verb flag.

## C: rounds

The `round` group is the orchestrator layer over the same slot registry (`.hv/workers.json`) and host package as `hv worker`. It adds no second state file. Each verb below owns its entry.

### hv round wait
hv round wait [<slot>...] [--timeout <seconds>] [--settle <seconds>] [--lines <n>]
repo: none
data: {"slot": string, "state": string, "evidence": string, "source": "herdr-event" | "snapshot" | "poll", "waited": number}

old: none (new in C1)
note: blocks until one watched slot needs attention, then returns that slot. Watched slots are the named ones, or, when none is named, every registered slot that has a `handle` and whose recorded `state` is not `idle`. Pool init seeds every slot `idle` and gives a tmux slot a nominal handle before anything runs in it, and `worker poll` treats a recorded `idle` as already reported, so an idle slot is not watched unless named, or one parked slot would end every wait at once. `worker dispatch` records `busy`, which arms the slot. A slot with no handle is skipped, not an error, unless it was named.
note: "needs attention" is the `hv worker poll` classification, not the host's raw status: `idle`, `blocked`, `done`, `dead`, `limited`, `needs-permission` or `unknown` (UNKNOWN is surfaced, never treated as finished). `busy` keeps waiting. `state` is lowercased, `evidence` is the same line `worker poll` reports.
note: the host only wakes the verb, it never decides. On herdr a status event for a watched pane, on tmux a change in a watched pane's text, triggers a re-classification through the `worker poll` code, so sentinels (`HV-DONE`, `HV-BLOCKED`), `limited` and `dead` outrank the host's native state exactly as in `worker poll`.
note: a slot that already needs attention when the verb starts is returned at once, `source: "snapshot"`, so an event that fired before the call is never lost. When several slots qualify, the first in registry order wins. The wait does not consume anything: calling it again returns the same slot until the orchestrator acts on it.
note: herdr (0.9.x, pinned; any other minor exits 5): wakes on `pane.agent_status_changed` over one socket subscription for all watched panes (`source: "herdr-event"`). tmux has no agent status and no event stream, so the verb re-captures the watched panes every `--settle` seconds (default 5) inside the process and re-classifies on change (`source: "poll"`). The orchestrator's context never sees either loop.
note: read-only. The verb does not write `.hv/workers.json`, so there is no `changed` field; recording a slot's new state stays with `hv worker poll`.
note: a timeout is a normal outcome, not a fault: exit 1 with `timedOut: true`, because the verb exists to answer "which slot needs me" and the answer is "none yet". Exit 6 is not used, since the conventions send it `error` alone and reserve it for faults a retry clears. `--timeout` defaults to 0, meaning wait indefinitely. A caller whose shell cuts commands short raises the cap (`BASH_MAX_TIMEOUT_MS` in Claude Code) or loops on a finite `--timeout`.
note: no `HV_TEST_*` hooks. The smoke section drives a fake `herdr` binary plus a fake unix-socket server (`HERDR_SOCKET_PATH`), and `test/fakes/tmux`.

- **Round slot.** The `slot` of A7 plus derived fields. C2 stores nothing new: the issue is the slot's `task` (or, when `task` is not a number, the leading number of the branch `<agent>/<issue>-<slug>`), the PR is `pr`, and the host state is read live. Later C issues (tier, escalations) add optional slot fields with their own entries.
- **Sources.** Rows come from the union of three sources, so a restart works with an empty registry: the registry slots; the git worktrees under `<root>/.worktrees/` (a worktree on `park/<name>` is a parked slot named `<name>`, on `<name>/<issue>-<slug>` a slot working that issue); and the host snapshot, whose agents are matched to a row by `handle` (tab id), else by `cwd` equal to the row's worktree. Open PRs come from the forge by head branch, issue labels from the tracker.
- **Degraded sources.** A source that is unavailable (host not running, forge or tracker CLI missing or failing) is named in `unavailable` and `warnings`, and the drift kinds that need it are skipped. The verbs still exit 0: a restart usually finds herdr down.
- **Drift kinds.** `dead-tab`: slot has a `handle` and the host has no live agent for it. `unclaimed-tab`: a live agent whose `cwd` is inside `.worktrees/` matches no row. `unregistered-worktree`: a worktree under `.worktrees/` has no registry slot. `branch-no-pr`: the slot's branch is neither its parking branch nor the base, has commits ahead of the base, and has no open PR. `pr-unrecorded`: an open PR has the slot's branch as head and `pr` is empty. `pr-stale`: `pr` names a PR that is merged or closed while the slot still holds its task. `label-missing`: the slot holds an issue and the issue lacks the `in-progress` label. `label-orphan`: an issue has `in-progress` and no slot holds it.
- **Safe repairs** (`reconcile --apply` only, each additive or derived): `dead-tab` clears `handle` and sets `state` to `dead`; `unregistered-worktree` registers the slot; `pr-unrecorded` records `pr`; `label-missing` adds `in-progress`. Never repaired: `unclaimed-tab` (a tab may be a live worker), `branch-no-pr` (opening a PR is the worker's act), `pr-stale` and `label-orphan` (resetting a slot and removing the label are the orchestrator's calls, `worker.md`).
- **Host snapshot.** herdr: `herdr api snapshot` (pin 0.9.x), reading `agents[]` (`tab_id`, `cwd`, `agent_status`, `name`). tmux: `tmux list-windows` with the pane's current path. Both sit behind a new optional `host.Snapshotter`, in `internal/host/snapshot.go`; the `Host` interface does not change.

- **Escalation** (C4, #60). A question the orchestrator puts to the human on an issue or PR thread, with a herdr notification alongside. Open escalations live in a top-level `escalations` list in `.hv/workers.json`, beside `slots`, because an escalation need not belong to a slot. An entry is `{"id": string, "kind": "issue" | "pr", "number": number, "slot"?: string, "title": string, "commentId": string, "sentAt": string, "deadline"?: string, "notified": bool, "status": "pending" | "answered", "answer"?: answer}`, with `answer` `{"commentId": string, "author": string, "body": string, "seenAt": string}`. `id` is `e<N>`, N one more than the highest in the list. - **Marker.** Every comment hv posts for an escalation ends with the line `<!-- hv:escalation <id> -->`, invisible once rendered. Any comment carrying a `<!-- hv:` marker is hv's own and is never an answer.
- **Answer rule.** The orchestrator, the workers and the human usually post as the same account, so the author decides nothing. The answer to an escalation is the first comment on its thread that comes after the escalation comment in the forge's oldest-first order and carries no `<!-- hv:` marker (maintainer ruling, 2026-10-03, relayed by the orchestrator in round 4). The rule therefore relies on hv marking every comment it posts; a comment posted outside hv (raw `gh`, a bot) on a thread with a pending escalation reads as its answer, so `check` returns the answer's body for the orchestrator to read before acting on it.
- **One per thread.** At most one pending escalation per issue or PR, so a single answer can never be read as answering two questions.

### C3: round start, candidates, assign, wind-down

C3 (#59, absorbing #40 and #41) adds the round lifecycle over the same registry. Orchestrator rulings (round 4, `c-rulings.md`): no second state file unless a need does not fit `workers.json`; the autonomy axis is a new key, not `autonomy.level`; the file-overlap rule is concrete and states what it cannot catch.

- **Round config.** Four keys, all silent defaults (the `ship.mergeApproval` pattern; not seeded by init). `round.scope` is `slate`, `milestone` or `next`, default `milestone`. `round.roster` is a list of agent names, default `["ben","dana","nia","kit"]`. `round.brief` is the path the worker pointer names, default `""` (see **Brief pointer**). `round.sharedPaths` is a list of repo-relative globs the overlap check ignores, default `[]`. `autonomy.level` (off/auto/loop) is untouched: it says how far skills chain on their own, `round.scope` says which issues a round may take.
- **Scope.** The candidate set is the open, unheld items of: `slate` the round's recorded slate and nothing else; `milestone` the active milestones (`hv milestone active`, then `hv backlog ids --milestone`); `next` the same, and when none of those is left to assign, the items of the first `planned` milestone whose dependencies are all shipped (`milestone list`, `ready`). The scope is enforced by `assign`, not advisory: an issue outside it is refused. Choosing `slate` is how the maintainer approves exactly what a round may touch; `milestone` is the #44 default (slate confirmed once, by the orchestrator, from `start`'s candidates); `next` lets an unattended round roll over.
- **Registry fields.** C3 adds optional fields to `.hv/workers.json`, all absent until written. Top level: `scope` (string, the scope the round started with) and `slate` (`[]string`, issue IDs in rule-11 spelling, present only for `slate`). Per slot: `claimId` (string, the `item claim` id `assign` took, released by `wind-down` and by C10's return). The issue a slot holds stays in `task` and its branch in `branch`; the top-level `round` number is the one `worker dispatch --round` already writes.
- **Lease.** One orchestrator per repo, keyed on `git rev-parse --git-common-dir` so every worktree of the repo shares it. It does not fit `workers.json`: that file lives under each worktree's own `.hv/`, so a second worktree sees an empty registry and a lock inside it protects nothing. The lease is `<git-common-dir>/hv/round-lease.json`: `{"pid": number, "start"?: number, "host": string, "pane"?: string, "paneHost"?: "herdr"|"tmux", "root": string, "round": number, "startedAt": string}`. `pid` is the orchestrator process, not the short-lived `hv`: the nearest ancestor that is not a shell, `env`, `timeout` or `hv` (in Claude Code, the `claude` process), else the parent. `start` is that process's start time (Linux `/proc/<pid>/stat` field 22), read to defeat PID reuse, absent where the platform has none. `pane` is `HERDR_PANE_ID` or `TMUX_PANE`. The lease is `live` when `host` is this host and the pid runs with the same `start`; `stale` when `host` is this host and the pid is gone or its start differs; `foreign` when `host` differs (cannot be checked, treated as live and named). `pid`, `host` and `pane` are overridable by `--holder-pid` for harnesses whose ancestry is not discoverable.
- **Lease seam (C2, C6).** `internal/round` exports `ReadLease(root) (Lease, LeaseState, error)` with `LeaseState` one of `none`, `live`, `stale`, `foreign`, and `ClearStaleLease(root) (Lease, bool, error)`, which removes only a `stale` lease. C3 owns both; `reconcile` and `reap` call them and write nothing of their own. `reconcile` gets one new drift kind, `lease-stale` (a `stale` lease; the finding's `detail` names the holder), never repaired by `--apply`; `hv reap` lists it as a candidate and clears it through `ClearStaleLease`. `hv round start` also reclaims a stale lease itself, since a provably dead holder needs no human, with the warning `reclaimed stale lease held by pid <n>`.
- **Readiness.** `candidates` and `assign` run three checks per item, each reported in `checks` as `{"name": "criteria"|"dependencies"|"overlap", "ok": bool, "detail": []string}`:
  1. `criteria`: the `hv item ready` rule verbatim (acceptance criteria, or a design or plan note); its `reasons` are the detail.
  2. `dependencies`: every reference in the item's `## Depends on` section (issue body, or the detail file in file mode) must be done: closed in issue mode, archived in file mode. A reference in the item's own ID spelling (`#57`, `57`, `B07`) is looked up; any other reference (`owner/repo#N`, a URL) cannot be verified and fails the check (`cannot verify <ref>`). An item with no such section has no dependencies. An open dependency with a PR is not done.
  3. `overlap`: no file overlap with an in-flight item. In flight means a slot in this registry holding a `task` other than this item. The footprint of an item is the `## Files` section when present (one path or glob per bullet), otherwise every token of the body and comments that is a tracked path at the base (`git ls-files`) or a directory prefix of one (two or more segments, so `docs/` alone never counts), minus `round.sharedPaths`. The footprint of an in-flight item is its own footprint plus its slot's real changes (`git diff --name-only <base>...<branch>` and uncommitted paths in the slot's worktree). Two footprints overlap when they share a file or one names a directory holding the other's file. The check cannot catch: files an item will create, paths nobody wrote down, two items editing the same function or file under different names, generated files and registries every item touches (list those in `round.sharedPaths`), renames, work on another machine's round, and a stale issue text. It is a heuristic that fails closed on what it can see, so it stays on only because it is cheap to override (below).
- **Brief pointer.** `assign` hands the worker a short signed brief instead of the pasted contract (#41): its agent name, the round number, the path of the standing contract, the issue to read first with its thread (and the instruction to dispute the ticket before implementing if it is wrong or already decided), the branch, the sibling issues, and the answered decisions verbatim from `--body-file`. The contract is `references/worker-contract.md`, which C3 extends with a *Read the issue and dispute it* step. The path comes from `round.brief` when set, else `references/worker-contract.md` under `CLAUDE_PLUGIN_ROOT` when that is set, else under the project root; if none exists `assign` refuses before touching anything (`blockedBy: "brief missing"`). `/hv-work`'s own dispatch keeps pasting the contract; moving it to the pointer belongs to the orchestrate skill (C7).

### C5: merge policy and approval requests

C5 (#61) is the orchestrator side of the merge policy. Most of #61 shipped with B1 (#54): `ship.mergeApproval` (`none`, `all`, `paths`) and `ship.mergeApprovalPaths`, the `merge-approval` gate on `ship merge`, `ship pr-merge` and `worker gate`, and the path match against the PR's changed files. Under the default `none`, `worker gate` already merges a passing PR without a prompt. C5 adds the two missing pieces: the approval request goes out through the C4 escalation channel, and the human's answer comes back as a recorded B1 approval. It adds no verb and no config key, only two flags on `worker gate` and `ship pr-merge`.

- **Approval thread.** The thread a merge's approval request lives on: the PR (`kind` `pr`, its number) when the merge has one, else for `worker gate` the slot's issue (`kind` `issue`, the round slot's issue number). `ship merge` has no forge thread, so it takes neither flag and keeps `--confirm` from an `AskUserQuestion`.
- **`--escalate`.** When the `merge-approval` gate refuses, the verb also sends the approval request with `round escalate send` on the approval thread (`--slot` set for `worker gate`), then exits 4 as before, with the escalation in `data.escalation`. Title `Merge approval: PR #<n>` (or `Merge approval: <slot> (<branch>)` without a PR). The body names the policy (`all`, or `paths` with the matching files from `data.paths`) and ends: ``Reply `approve`, `approved`, `yes`, `lgtm` or `ship it` to merge. Any other reply holds the merge.`` When an escalation on that thread is already pending, the verb sends nothing and returns the pending one, so a re-gate in a loop never posts twice. With no gate to clear (the policy does not cover the merge), `--escalate` is accepted and does nothing. A send failure is a `warnings` entry; the refusal stands.
- **`--approval <id>`.** Clears the `merge-approval` gate with a recorded answer instead of `--confirm`. It reads escalation `<id>` from `.hv/workers.json` and makes no forge call, so run `round escalate check` first. Checks, in order, all before anything changes:
  - unknown `<id>`: exit 3;
  - the escalation is not on this merge's approval thread: exit 2;
  - `status` is not `answered` (pending, or timed out with no answer): exit 4, `{"blockedBy": "approval pending", "escalation": string, "status": string, "changed": false}`;
  - the answer does not approve: exit 4, `{"blockedBy": "approval declined", "escalation": string, "answer": string, "changed": false}`.
  An answer approves when the first word of its first non-blank line, lowercased with trailing punctuation removed, is in the allowlist `approve`, `approved`, `yes`, `lgtm`; or when that line's first two words, treated the same way, are `ship it`. `Approve.`, `YES, go ahead`, `lgtm!` and `Ship it.` approve; `no`, `yes-ish`, `please approve` and `ok` hold the merge. The allowlist lives in one function (maintainer ruling, relayed by the orchestrator in round 4: "Approve or yes words").
- **Recording.** A cleared `--approval` writes the B1 audit line with `note` set to the answer body verbatim and `escalation` set to `<id>`, exactly as `--confirm --confirm-note` would with the quoted answer. The escalation stays in the registry as the record of what the human said; the same answered escalation can clear a re-gate of the same thread (after a `stale` bounce, say).
- **Flag rules.** `--approval`, `--escalate` and `--confirm` are mutually exclusive (exit 2). `--approval` on a merge the policy does not cover is accepted and writes nothing, the same as `--confirm` (B1).
- **Skill routing.** `/hv-work`'s gate step and `/hv-review --queue` pass `--escalate` when the round is unattended (`autonomy.level` `loop`, or the orchestrator is driving herdr workers), record the escalation id against the slot or PR, keep working other slots, and re-gate with `--approval <id>` once `round escalate check` reports it answered. An `approval declined` refusal is surfaced and the slot is held, never retried. Interactive runs keep the `AskUserQuestion` plus `--confirm` path from B1.
- **Limits.** The approval is tied to the thread, not to a commit: commits pushed to the PR after the answer are covered by it. `worker gate`'s provenance and freshness checks still run on every re-gate, so a moved head is re-verified, but it is not re-approved.

### C9: worker tier and model

C9 (#75) lets the orchestrator choose how heavy a model each worker starts with, and tells the worker how to size its own subagents. Skills and briefs speak in **tiers**; config maps tiers to model names per harness kind, so nothing outside config names a model.

- **Tiers.** `light` (reading, searching, discovery), `standard` (writing code and tests), `heavy` (hard reasoning, design, tricky debugging), in that order. A harness **kind** is `claude` or `codex`.
- **Config.** Eight keys, all silent defaults (not seeded by init). `round.tier` is the default tier, `standard`. `round.tiers.<kind>.<tier>` is the model name: `claude` defaults to `haiku` for light and `opus` for heavy, and `standard` defaults to the value of `models.worker` (itself `sonnet` by default), so one knob governs the standard model and the two cannot drift; an explicit `round.tiers.claude.standard` wins; `codex` defaults to `""` for all three, because codex model names are not ours to fix and a codex worker is E1's. A kind is *configured* when any of its three tiers is non-empty. Validation (read through `internal/roundcfg`, so every verb that reads round config exits 70 on it): `claude` must be configured; a configured kind must have all three tiers non-empty (the error names the missing `round.tiers.<kind>.<tier>`); `round.tier` must be a tier. Unconfigured `codex` is not an error until a codex worker is asked for.
- **Choosing.** `hv round assign --tier <t>` picks the tier; omitted, it is `round.tier`. hv does not choose from the issue: size, type, labels and judgment belong to the orchestrate skill (C7). The config tier is a default, not a ceiling: a tier above it needs `--tier-reason <text>` (one line, exit 2 without), and any given reason is recorded. A tier at or below the default needs none. `--kind` is the harness kind of the worker, default the slot's recorded `kind`, else `claude`.
- **Resolving.** `model` is `round.tiers.<kind>.<tier>`. On a `claude` kind the default launch command is `claude --model <model> --dangerously-skip-permissions` (`models.worker` also drives `/hv-work`'s own dispatch, and is the default of the standard tier, above). A custom `work.workerCommand` receives the model only through a `{model}` placeholder in it; without one the tier is recorded but `model` is left out of the slot and `data`, and `assign` adds the warning `tier model not applied: work.workerCommand has no {model} placeholder`, because rewriting a command hv does not own would lie about what ran.
- **Codex.** The tier map, its validation and the resolution above are defined for `codex` and `--check-only` reports the model it would use. Starting a codex worker is E1 (#68), under "E: Codex workers".
- **Registry fields.** Optional per-slot fields, absent until `assign` writes them and cleared when the slot is parked (`wind-down`): `kind` (string), `tier` (string), `model` (string), `tierReason` (string). They are the round state C9 asks for; `round status` rows show them.
- **Brief.** The subagent guidance is split on purpose. The **standing rule**, harness-neutral and with no model names, lives in `references/worker-contract.md`: delegate reading and searching to a `light` subagent, code and tests to `standard`, and keep `heavy` for genuinely hard reasoning, using the tier map the pointer gives. The **resolved facts** for this worker live in the pointer brief `assign` writes: its own tier and model, the tier-to-model table of its kind, the reason when it is above the default, and the instruction to put `Worker tier: <tier> (<model>)` in its PR body, which is how the choice reaches the PR (workers write their own PR bodies, hv cannot).
- **Not in C9.** Picking the tier from the issue (C7), a tier per subagent call (the worker decides, by the rule), and showing `size` or priority in `candidates` to help the choice (the orchestrator reads the backlog).
### C10: round return, transfer, reclaim

C10 (#76) moves an issue that is already assigned. It builds on C3 (`assign` takes the claim, `claimId` on the slot, the lease) and C2 (`reconcile`). Orchestrator rulings (round 4, `c-rulings.md`): the claim lives on the tracker, through the same `item claim`, `item release` and `item state` calls `assign` makes; no local-only claims file; the note transfer hands over is a minimal stand-in for D1's.

- **Premise check.** Four points in #76 do not hold as written, and the entries below follow the code, not the ticket. (1) "Back to ready" is not a state: `item ready` is a property of the text (acceptance criteria or a design note), and the only tracker state `assign` sets is `in-progress`. Return puts the issue back in the candidate set by releasing the claim and clearing `in-progress`; `candidates` then lists it again with its checks. (2) "The branch stays" is false for a slot today: `worker reset` refuses to leave a branch with commits not on the base, and git will not check one branch out in two worktrees, so a slot cannot both keep the branch checked out and be free. The branch has to be pushed and the slot switched off it (**Park**). (3) "Reclaim from a stalled slot" needs a stall signal the registry does not hold: it has no activity time (**Stalled**). (4) "Transfer to the human" cannot be an assignee: the orchestrator and the human usually post as the same account (C4), so an assignee marks nothing; it is a label (**Claim on the tracker**).
- **Claim on the tracker.** The holder is the open claim comment `item claim` posts (`claimId` `<agent>@<round>`, C3) plus the `in-progress` label. `.hv/workers.json` mirrors it: the slot's `task` and `claimId`. A new top-level label role `issues.labels.needsHuman` (default `needs-human`) marks an issue handed to the human: no claim, no `in-progress`, the label on. Each verb below changes the tracker first and the registry second, so a crash between them leaves a mismatch reconcile reports and `--apply` repairs from the tracker, which wins. Return and transfer to a slot release the old claim before claiming anew, so an item is never claimed by two.
- **Park.** Return, transfer and reclaim free a slot with the same sequence, `internal/round.Park(slot)`: salvage the worktree if dirty (stage the dirty paths by name, never `-A`, and commit `wip: parked from <slot> (hv round <verb>)`), push the work branch to `origin` (`git push -u origin <branch>`, no force), and only if the push succeeded switch the worktree to `park/<agent>` at the base. A failed push leaves the slot as found, exit 5; the branch is never the only copy of the work. This is a second guard beside `worker reset`'s, not a change to it: reset still refuses a slot holding unmerged commits, because it cuts a fresh branch for new work; `Park` only moves the checkout off a branch that now exists on the remote. `worker reset` is the one that cuts the next issue's branch afterwards, so `assign` after a return behaves as on any parked slot. The salvage commit is the one thing a verb writes into a worker's branch. A commit that a hook rejects is exit 5 and the slot is left as found.
- **Stalled.** A slot is `stalled` when it holds an issue, its host agent is alive, and nothing has moved for `round.stallMinutes` (default 30, `0` turns the check off; a silent default like `round.scope`, not seeded by init). "Moved" is the newest of: the committer time of the branch tip when the branch has commits past the base; the newest mtime among the worktree's dirty paths (`git status --porcelain`, `stat`); and the slot's `activeAt`, a new optional registry field (RFC 3339 UTC) that `worker dispatch` stamps and `worker poll` re-stamps whenever the state it classifies differs from the recorded one. A worker editing without committing is therefore not stalled. A slot whose host agent is not alive is `dead`, not `stalled` (`dead-tab`, C2), and a slot waiting on an open escalation (C4) is never stalled. The signal that cannot be had is the host's raw agent-status churn: herdr events are not stored and `round wait` is read-only, so a hung agent that still repaints its status is judged on commits and files alone. Reconcile and reclaim compute this the same way, in `internal/round.Stalled(slot, now)`, with `now` injectable so the threshold is testable without sleeping.
- **Reconcile amendments (C2).** Two drift kinds, neither repaired by `--apply`'s existing rules except as noted. `stalled`: the rule above (`detail` carries the idle minutes and the signal that last moved). `claim-mismatch`: the tracker and the registry disagree about who holds an issue: the slot's `task` has no open claim by its `claimId` (or another claim holds it), or an open claim `<agent>@<round>` names a registry slot that does not hold that issue. `--apply` repairs only the registry side of an unambiguous mismatch (clears a `claimId` whose claim is gone; never edits the tracker), because the tracker is the source of truth and a human may have changed it on purpose. `label-orphan` and `label-missing` stay as C2 defined them.
- **Handoff note.** A stand-in for D1's note (#65), small enough that D1 can absorb it: one comment on the issue, posted by `return`, `transfer` and `reclaim`, ending with the marker `<!-- hv:handoff <from>@<round> -->` so C4's answer rule never reads it as an answer. Body: `**hv handoff** (<verb>, from <slot>)`, then four labelled lines `Branch:`, `Head:` (the pushed sha7 and subject), `State:` (committed, plus `salvage commit` when `Park` made one) and `Reason:`, then free text under `Done and next:` taken from `--note-file`. A receiving worker finds it by the marker; the pointer brief (C3) names the latest `hv:handoff` comment and the branch. When D1 lands, its format replaces this body and the marker stays.

If the reason is a wrong premise, the issue text is still wrong; the worker's comment is what the next reader sees, and fixing the ticket is the orchestrator's call.
note: `salvaged` is true when `Park` made a salvage commit. `released` is false when no claim matched (a claim already gone is not an error).

### hv round reclaim
hv round reclaim <slot> [--force] [--note-file <path|->]
repo: none
data: {"slot": string, "issue"?: string, "branch"?: string, "head"?: string, "health": "dead"|"stalled"|"healthy"|"idle", "salvaged": bool, "released": bool, "parked": bool, "changed": bool}
exit: 3 when there is no project root or the slot is unknown; 4 with `blockedBy` one of `no round` (the caller holds no lease), `healthy` (the slot is neither dead nor stalled and `--force` is absent), `live agent` (see below); 5 when git, the push or the tracker fails (the slot is left as found); 6 when the registry lock times out

note: the orchestrator's verb for a slot reconcile reports as `dead-tab`, `dead` state or `stalled`. note: `live agent`: a stalled slot has a live host agent, and parking its worktree under a running agent would leave the agent editing a branch it is no longer on. A `dead` slot has nothing to kill.

The slot is parked and the issue assignable, with the branch pushed and named in the comment. note: `reap` (C6) may reclaim `dead` slots only, never `stalled` ones (maintainer ruling, round 4). A worker in a long test run makes no commits and no status change, so it reads as stalled, and an unattended `reap --apply` would kill it. `stalled` is reported by reconcile, and reclaiming it is always an explicit orchestrator call. `reap` passes no `--force` and checks `health` is `dead` before calling.

## E: Codex workers

E1 (#68) runs OpenAI's Codex CLI as a round or pool worker beside Claude Code. It adds no verb: `worker dispatch` and `round assign` take `--kind codex`, `doctor` gains a `codex` check. A codex worker is a visible TUI session in a herdr tab, like a claude one; headless `codex exec` stays out (#44).

- **Kind.** `--kind` picks the harness; the default is the slot's recorded `kind`, else `claude`. `assign` records it on the slot (C9) and passes it to dispatch. The kind selects the launch command, and under herdr the command's binary must match the kind (`claude` or `codex`, by basename after any leading `KEY=VALUE` tokens), so `herdr agent start --kind` is derived from the command, never assumed.
- **Launch command.** New key `work.codexCommand`, a silent default (not seeded by init): `codex --model {model} --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust --no-daemon --no-alt-screen`. `{model}` takes the tier's model, as in `work.workerCommand` (C9); with no model chosen (a bare `worker dispatch`) the default drops `--model {model}` and Codex uses its own default, while a custom command that still holds `{model}` exits 2. The bypass flag is the codex twin of `--dangerously-skip-permissions`, for the same reason (nobody answers prompts in a worker pane; scope, not gating, bounds it). `--no-daemon` keeps the session in the pane's own process tree: a session hosted by Codex's background app-server would outlive `tab close`, and dispatch's kill must be provable. `--no-alt-screen` keeps the pane's scrollback readable: herdr refuses `agent read --source recent-unwrapped` while a Codex agent in the alternate screen is working, which would leave `worker poll` blind mid-turn (seen live, #70 spike). `--dangerously-bypass-hook-trust` is there because Codex opens a hook-review screen on the first prompt for any untrusted hook, including herdr's own integration hook in every slot home; the screen swallows the prompt and herdr reports `idle` or `working`, never `blocked`, so no dialog handler sees it (seen live, #70 spike). The worker already bypasses the sandbox and approvals, so trusting hooks unread adds little; the Claude-worker parity is `--dangerously-skip-permissions` (maintainer ruling, round 4). The resume guard also refuses codex's `resume` and `fork` subcommands.
- **Codex home.** Each slot has its own `CODEX_HOME` at `<git-common-dir>/hv/codex/<slot>`, never `~/.codex`. It holds the slot's login, sessions, history and herdr integration, so two slots share no auth or session state. It lives beside the round lease rather than inside the worktree: inside, it would dirty `git status`, trip the reset guard and sit in the worker's own tree. It is outside `.worktrees/`, so `reap` never sees it, and it survives `wind-down` and resets, which keeps the login. hv creates it (0700) on the first codex dispatch to the slot and never deletes it.
- **Seeding.** On creation hv writes `config.toml` into the home, and only when the file is absent: the slot's worktree trusted (`[projects."<worktree>"] trust_level = "trusted"`) and `check_for_update_on_startup = false`, so neither dialog opens in an unattended pane. Under herdr, when `CODEX_HOME=<home> herdr integration status` does not report codex `current`, hv runs `CODEX_HOME=<home> herdr integration install codex`, the codex counterpart of the claude integration the `hook` check asks for. hv never writes `auth.json` and never copies one.
- **Login.** hv does not log a slot in. Before anything is marked, `assign` and `dispatch` run `CODEX_HOME=<home> codex login status`; a non-zero exit is exit 5 with the hint `CODEX_HOME=<home> codex login`, which the maintainer runs once per slot. Copying an existing `auth.json` into a slot home is not a shortcut: a ChatGPT login carries a rotating refresh token, so two copies refresh independently and can invalidate each other, including the maintainer's own login in `~/.codex`.
- **Version.** The supported Codex CLI range is pinned in hv: `>= 0.159.0, < 0.160.0` (the version tested, 0.159.2, as herdr is pinned to 0.9.x). It is read from `codex --version` (`codex-cli X.Y.Z`; anything else counts as unsupported). Outside the range, `assign` and `dispatch` refuse with exit 4, `blockedBy: "codex version"`, before anything is marked; `--accept-codex-version` lets one call through and adds the warning `codex X.Y.Z is outside the supported range <range>`. The flag is not `--force` (rule 5). `doctor` reports the same check.
- **Host.** herdr only: `tab create` passes `--env CODEX_HOME=<home>` (the account is fixed at tab creation, as `CLAUDE_CONFIG_DIR` is) and `agent start --kind codex`. `work.accounts` and its usage meter are Anthropic's and are skipped for a codex slot: the slot's home is its account, so there is nothing to rotate until Codex has a meter. Under tmux a codex dispatch exits 5 (`codex workers need work.dispatch=herdr`): the tmux host detects a booted session from Claude Code's screen text and has no codex equivalent.
- **Startup dialogs.** herdr reports Codex's folder-trust, update and hook-review screens as `idle` or `working`, never `blocked`, so the herdr dialog handler (`agent_not_ready` at start) cannot see them. They are prevented instead: the seeded `config.toml` covers folder trust and the update check, and `--dangerously-bypass-hook-trust` covers hooks. The texts are recorded in the #70 spike.
- **Classification.** Unchanged code: herdr reports the codex agent's state natively, and `worker poll` and `round wait` apply the same sentinels (`HV-DONE`, `HV-BLOCKED`) on top. `limited` gains Codex's usage-limit text once recorded live. The working, idle and blocked check on the Codex TUI is manual and recorded in the PR (#68).
- **`hv doctor` `codex` check.** Placed after `hook`. `skip` when codex is not on PATH and no slot has a codex home. Otherwise `fail` when codex is missing (a slot has a home), its version is unreadable or outside the range (hint: install codex-cli 0.159.x), or a slot home is not logged in (hint `CODEX_HOME=<home> codex login`) or, under herdr, lacks the integration (hint `CODEX_HOME=<home> herdr integration install codex`). `detail` names the version and the homes checked. `codex --version` runs with `CODEX_HOME` set to a slot home when one exists, so the check never needs `~/.codex`.
- **Not in E1.** Codex subagents and solo mode (E3, #70, then C8), a Codex usage meter, codex under tmux, a second-opinion runner (#158 retired it).

### D1: statusline dump, Stop hook and handoff

D1 (#65) lets a long-running Claude orchestrator hand off and exit before its context or usage runs out. Three small pieces: a **state dump** fed by the statusline, a **Stop hook** that blocks above a context threshold, and a **SessionStart hook** that injects the handoff into the next session. It acts only on the orchestrator. Restarting the pane after the exit is D2 (#66), and what to do about a usage limit is D3 (#67); D1 writes the state they read and starts nothing.

Status: **ratified by the maintainer, round 4** (AskUserQuestion, relayed by the orchestrator). Statusline: "Wrapper", so `--wrap-statusline`, record the original, uninstall restores it exactly, and `dump` swallows its own errors. Hook scope: "Project-local", `.claude/settings.local.json`. Handoff file: `.hv/handoff/<base>.md`, delivered by the SessionStart hook. The 75% threshold default is ratified as configurable. The context fallback from `current_usage` and `context_window_size` is accepted; `used_percentage` stays unverified. If a plugin cannot register a `statusLine`, the wrapper does not need it to. Still my own calls, unratified: the verb names (`hv hook install`, not `hv statusline install`, since one command installs the hooks and the statusline together), the three other config defaults, the loop-prevention counts and the lease-based orchestrator test.

- **The session state file.** `<git-common-dir>/hv/session/<session_id>.json`, written atomically (`fsio`) on every statusline refresh. It sits next to the round lease for the same reason: per repo, shared by every worktree, never tracked, and no new `.hv/.gitignore` entry. Fields: `sessionId`, `cwd`, `updatedAt` (RFC 3339), `contextPct` (number or absent), `rateLimits` (the statusline's `rate_limits` object verbatim, absent when the session has none), and `raw` (the whole input JSON, so D3 and later phases read fields D1 did not anticipate). `contextPct` is `context_window.used_percentage` when present; otherwise it is derived from `context_window.current_usage` (input, cache-creation and cache-read tokens) over `context_window.context_window_size`; absent when neither exists. Files for a session untouched for 24 h are removed by the next dump.
- **"The orchestrator."** The session whose Claude process holds the round lease (`internal/roundlease`, C3), matched with `Holder.SameAs` on the nearest non-shell ancestor, as `hv round start` records it. No lease, or a lease held by another process, means the hook is a no-op and exits 0 with no output. This is how the plugin or settings registration can be wide without touching workers, which also run Claude but never hold the lease. The dump itself is written for every session, because the statusline cannot know which it is.

### hv statusline dump
hv statusline dump [--then <command>]
repo: none
data: none. Prints nothing of its own; the verb is a statusline command, not a query.
exit: always 0. A statusline that fails blanks the user's bar, so every error (unreadable stdin, no git dir, unwritable state directory) is swallowed and goes to stderr only when `HV_STATUSLINE_DEBUG` is set.
old: none (new in D1)
note: reads the session JSON from stdin, writes the state file, then runs `--then` (through `sh -c`) with the same bytes on stdin and the real stdout and stderr, and returns after it. Without `--then` it prints nothing, which leaves an empty statusline; `hv hook install` never installs that form over an existing statusline (see below). The dump runs first and its failure never skips the command. `--then` exiting non-zero still exits 0, with the command's stdout passed through unchanged.
note: no global `--json`: stdout belongs to the wrapped command. The verb rejects `--json` (exit 2).
env: `HV_TEST_NOW=<rfc3339>` fixes `updatedAt` and the 24 h expiry. Not part of the CLI.

### hv hook stop
hv hook stop
repo: none
data: none. The verb speaks Claude Code's hook protocol: JSON on stdout, exit 0.
exit: always 0, including on a state it cannot read: a broken hook must never wedge the orchestrator in a block loop.
old: none (new in D1)
note: reads the Stop payload on stdin (`session_id`, `stop_hook_active`, `cwd`). Passes (no output) unless all hold: this session is the orchestrator; its state file exists and its `updatedAt` is no older than `orchestrator.stateMaxAgeSeconds` (a stale reading is not acted on); `contextPct` is at or above `orchestrator.handoffThreshold`; and no fresh handoff exists yet. Otherwise prints `{"decision":"block","reason":"…"}` where the reason names the percentage and the threshold and tells the orchestrator to write the handoff to the handoff path below, commit nothing it does not own, and run `/exit`.
note: loop prevention. When the payload carries `stop_hook_active` true and the handoff file now exists and is newer than the block, the hook passes: the orchestrator did what it was told and is exiting. When `stop_hook_active` is true and no handoff exists, the hook blocks once more, at most `orchestrator.handoffMaxBlocks` times per session (default 2, counted in the state file), then passes and records `handoffFailed: true` in the state file so D2's breaker reads it. A session that cannot write a handoff must not be held forever.
env: `HV_TEST_NOW=<rfc3339>` fixes the clock; `HV_TEST_HOLDER_PID=<pid>` stands in for the nearest non-shell ancestor in the lease test (also on `session-start`). Not part of the CLI.
note: the percentage is read from the state file, not the payload, because the Stop payload carries no context figure (Claude Code hooks reference, checked in round 4). The reading is one statusline refresh old at worst.

### hv hook session-start
hv hook session-start
repo: none
data: none (hook protocol: JSON with `hookSpecificOutput.additionalContext`, exit 0)
exit: always 0.
old: none (new in D1)
note: acts when `source` is `startup` or `clear`, this session holds the round lease, and the handoff file exists. It prints the handoff body as `additionalContext`, prefixed `Handoff from the previous orchestrator session, now consumed:`, then deletes the file. `resume`, `compact` and `fork` keep the file: the session already has its context. Consume-on-inject means a crash between the print and the model reading it loses the handoff; the verb therefore moves the file to `<handoff path>.consumed` instead of deleting it, and the next write of a handoff replaces that. A read failure leaves the file and prints nothing.
note: lease timing. `hv round start` takes the lease; a fresh session that has not run it yet holds nothing, so the hook passes and the file waits. D2 restarts the orchestrator with the lease still free, so the restarted session's first act is `hv round start`; the orchestrate skill (C7, #63) says so and says to read the handoff then. The hook also injects when no live lease exists (none, or a stale one whose holder is gone, which is what an exited orchestrator leaves) and the handoff is younger than `orchestrator.handoffMaxAgeSeconds` and was written by a Stop-hook block (it carries the marker below), so an orchestrator restarted before it reclaims the lease still gets it.

#### The handoff file
`.hv/handoff/<base>.md`, the path `hv status handoff <base> --canonical` already returns (base is `git.base`, `main` here). The file carries first line `<!-- hv-handoff: orchestrator -->` and `<!-- written YYYY-MM-DDTHH:MM:SSZ -->`; the body follows `references/handoff-template.md`, with a `## Round state` section the orchestrator adds (slots, who holds what, merges pending, escalations open). `/hv-pause` already writes this file for a session on the base branch, so the user's manual pause and the forced one are the same artefact, and `/hv-next` consumes either. "Fresh" is `updatedAt` within `orchestrator.handoffMaxAgeSeconds` (default 900). D2 reads the same path and the same freshness rule; D1 owns the definition.

### hv hook install
hv hook install [--scope <project-local|project|user>] [--wrap-statusline]
repo: none
data: {"scope": string, "settingsPath": string, "hooks": []string, "statusline": "installed" | "wrapped" | "kept" | "present", "changed": bool}
exit: 4 when a plain install would replace or shadow a statusline, that is one already in the chosen file or in a lower-precedence scope, and `--wrap-statusline` is not given (`blockedBy`: `statusline exists`, `changed` false, nothing written); 3 when a project scope (`project-local` included) is asked outside a project root; 70 when the chosen settings file does not parse (hv never overwrites it)
old: none (new in D1)
note: merges into the chosen settings file and never replaces anything it did not write. It adds a `Stop` hook running `hv hook stop`, a `SessionStart` hook running `hv hook session-start` (matcher `^(startup|clear)$`), and a `statusLine` of `hv statusline dump`. The hooks carry a marker in their command (`# hv-hook`) so a re-run finds and updates them instead of stacking duplicates; re-running with nothing to change is `changed: false`.
note: **statusline coexistence.** If any scope already sets a statusLine, plain `install` refuses (exit 4). With `--wrap-statusline` it rewrites the effective one to `hv statusline dump --then '<original command>'` in the scope being written, and records the original beside the entry (`"hvWrapped": "<original>"`) so `uninstall` restores it exactly. When the original came from another scope's file, the new entry also carries `"hvWrappedFrom": "<scope>"` and `uninstall` deletes the entry instead of restoring a copy. The settings file is rewritten in the `internal/jsonx` form (two-space indent, key order kept, non-ASCII as `\uXXXX`), so a file in that form round-trips byte for byte; another layout is normalised on the first write. The original is read from the highest-precedence scope that sets one (project-local, then project, then user), and written to the chosen scope: wrapping a user-level statusline from `project-local` leaves the user file untouched and shadows it only inside this repo. `statusline` in `data` says which happened: `installed` (none before), `wrapped`, `kept` (an hv-wrapped one was already there), `present` (a statusline in a higher-precedence scope than the chosen file, or an hv one in another scope, already wins; the hooks still install and the statusline is left alone).
note: default scope is `project-local`, `.claude/settings.local.json` in the project root, which Claude Code treats as per-developer and does not commit. Only one scope per call.

#### Config
Four keys, all silent defaults (not seeded by init), under `orchestrator`: `handoffThreshold` (integer percent, 1 to 100, default **75**), `stateMaxAgeSeconds` (default 120), `handoffMaxAgeSeconds` (default 900), `handoffMaxBlocks` (default 2). Documented in the five places the project rules name, and read through one `internal/` accessor so the hooks and doctor agree; an out-of-range value exits 70 for every verb that reads it, and the hooks treat it as a pass, never a block.

#### Doctor
Two checks, appended after `hook` (the existing `hook` check is herdr's agent integration and keeps its name): `statusline` (the effective statusLine, read through Claude Code's precedence, runs `hv statusline dump`, directly or through `--then`; `skip` when no orchestrator account or settings file is in scope) and `stop-hook` (a Stop and a SessionStart entry marked `# hv-hook` exist at some scope and their command resolves to the running `hv`; `fail` with the hint `hv hook install`). Both are read-only, `pass`/`fail`/`skip` as the other checks, and both look at every account's `configDir` settings plus the project's, since the maintainer runs `.claude-personal` and `.claude-work`.

#### Tests (acceptance → check)
- State file updates on each refresh: smoke section 90 feeds three JSON payloads through `dump` and reads `updatedAt` and `contextPct` change; a payload without `used_percentage` derives it from `current_usage`.
- Above the threshold the Stop hook blocks, below it passes: section 91 with a fixture lease holder, at 74, 75 and 99; no lease passes at 99.
- Loop prevention: `stop_hook_active` with and without a handoff, and the `handoffMaxBlocks` cap.
- Fresh session receives and consumes the handoff: `session-start` on `startup` injects and renames; on `resume` it keeps the file.
- Install and uninstall round-trip: a fixture settings file with an existing statusline is wrapped and restored byte for byte; a re-run changes nothing.
- Doctor: the two checks against fixture settings, missing, wrapped and current.
- The Go gate for `internal/hook` (new), `internal/doctor`, `internal/roundlease` readers and `cmd/hv`; frozen scenarios for the five verbs.

#### Rulings and what is still mine
Ratified (round 4): the wrapper for statusline coexistence, `project-local` as the install scope, `.hv/handoff/<base>.md` as the handoff file with SessionStart delivery, 75 as a configurable default threshold, and the `current_usage` fallback. Unverified and noted for the PR: `context_window.used_percentage`; `rate_limits.five_hour|seven_day.{used_percentage,resets_at}` are confirmed in use by the maintainer's own statusline script. The wrapper's cost is that the user's script runs as a child of `hv` on every refresh, which is why `dump` swallows every error. A root `HANDOFF.md` was rejected because it would dirty the base checkout that `hv round wind-down` requires clean; with the hooks uninstalled a restarted orchestrator reads nothing and `/hv-next` is the manual route.

My own calls, unratified: verb names; `stateMaxAgeSeconds` 120, `handoffMaxAgeSeconds` 900 and `handoffMaxBlocks` 2; that "orchestrator" means the lease holder; and shipping D1 without waiting for #63, whose only link is one line in the orchestrate skill (PR #194) telling a restarted orchestrator to run `hv round start` and read the handoff.

Not in D1: restarting the pane (D2), limit handling (D3), a non-Claude orchestrator, and any change to how `/hv-pause` writes.
